# v9.0 preparation: MariaDB, LDAPS, and role-based access

This package is a **preparation release**, not a v9.0 server update. The
included portal application remains the known-good v8.6.1 application. Do not
install it over a production portal expecting MariaDB or LDAP logins to work.

Its purpose is to freeze the v9.0 design, configuration shape, database schema
baseline, security boundaries, and acceptance criteria before implementation.

## v9.0 scope

1. Move local portal accounts, roles, sessions, audit records, template access,
   and operational settings from SQLite to MariaDB.
2. Use Argon2id for local-password hashes. Passwords are never encrypted or
   stored in plaintext.
3. Keep local authentication available as a protected break-glass path after
   AD/LDAP is enabled.
4. Add optional LDAPS configuration, certificate validation, connection test,
   user login, AD-group import, and role mapping.
5. Replace the current `admin`/`user` model with permissions assigned through
   roles. Initial roles: Platform Admin, Lab Manager, Template Approver, Lab
   Editor, Lab Operator, Viewer, and Auditor.
6. Offer an optional, separately deployed phpMyAdmin link for Platform Admins.
   It is not embedded in the portal and is not an authorisation boundary.

## Security decisions

- LDAPS only: certificate validation is required. The configuration accepts a
  corporate CA certificate bundle; plain LDAP is not offered.
- The directory bind account is read-only and has only the directory-search
  rights it requires. Its secret is stored outside source control with file
  permissions restricted to the service account.
- LDAP passwords are passed only to the directory for authentication and are
  never stored in MariaDB or portal logs.
- The browser session remains opaque and server-side. Database session tokens
  are stored as hashes and retain v8.5.8 expiry/revocation behaviour.
- phpMyAdmin must have its own HTTPS, network/AD-group, and MariaDB privilege
  protections. A portal menu link alone does not protect a database.

## Delivery sequence

1. Provision MariaDB, apply `database/001_mariadb_schema.sql`, and create
   application and migration accounts with least privileges.
2. Add a database abstraction and a safe one-time SQLite-to-MariaDB migration.
   Keep a backup of `data/audit.db` and make the migration idempotent.
3. Introduce roles and permissions while mapping current `admin` to Platform
   Admin and current `user` to Lab Editor during migration.
4. Add local Argon2id password rehashing at successful login, then require
   Argon2id for new or changed passwords.
5. Add the Administrator LDAPS configuration screen, CA upload, encrypted
   secret storage, test connection, group import, and role mappings.
6. Add authentication provider selection to the login page and validate that a
   disabled LDAP configuration cannot lock out local Platform Admin accounts.
7. Add syslog forwarding as an optional delivery channel; MariaDB remains the
   system of record for portal audit events.

## Acceptance criteria

- Existing v8.x local users can still sign in after migration.
- A local Platform Admin can administer the portal while AD is unavailable.
- Invalid, expired, or untrusted LDAPS certificates fail closed.
- Imported AD groups can be mapped to one or more portal roles; a group change
  takes effect at the next login.
- No LDAP password, MariaDB password, bind secret, or session token appears in
  portal logs, audit records, or error pages.
- Role permissions are enforced on the server for every lab, backup, template,
  user, audit, and database-administration action.
- phpMyAdmin is reachable only through its independent administrative controls
  and uses individual MariaDB accounts without `root` access.
